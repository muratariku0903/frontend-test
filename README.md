## 追加仕様
### 新規作成：ダイアログで入力してから作成する
- 要件は「サイドバーの『+』ボタンでページを追加できる」ことのみで、作成時の入力方法や初期値は決められておらず、デザインにも作成用の画面はない。
- そこで、「New page」を押すとダイアログを開き、タイトルと本文を入力して、両方が制約（タイトル 1〜50 文字、本文 10〜2000 文字）を満たしたときだけ作成する方式とした。

## 技術選定

### フレームワーク：React + Vite

- 今回は既存の REST API を呼ぶだけの SPA で、SEO や SSR は必要ない。
- API サーバーも別に存在するため、Next.js などの SSR 対応フレームワークを使う利点が小さく、Vite による SPA 構成が最もシンプルだと判断した。
- 目安の 8 時間で品質を確保するため、使い慣れていて設計の判断に迷いが少ない技術を選んだ。

### データ取得：TanStack Query

- サイドバーとメインエリアは同じデータを 2 か所に表示しており、作成・削除・タイトル編集のたびに両方を最新の状態にする必要があると考えた。
- TanStack Query を使うと、更新後にクエリキー単位で再取得を指示でき、ローディングやエラーの状態も宣言的に扱える。
- React Router のデータ APIも検討したが、キャッシュがないことと、更新後の再取得の範囲を細かく制御しにくいことから採用しなかった。

### フォームとバリデーション：react-hook-form + zod

- 入力値、一度入力したかどうか、エラー、保存できるかといったフォームの状態を自前で管理すると、state と条件分岐が増えて読みにくくなるため、React Hook Form に任せた。
- 入力チェックのルールは Zod のスキーマとして宣言的に書き、作成と更新で同じスキーマを使い回せるようにした。

### スタイリング：Tailwind CSS

- 普段から使っており、8 時間という実装時間の中でデザインを素早く再現できると考えた。
- 色やフォントは `@theme` にトークンとして定義し、仕様の値との対応が分かりやすい。

### テスト：Vitest + React Testing Library + MSW

- **Vitest**：Vite の設定をそのまま使え、追加の設定がほとんど要らない。
- **React Testing Library + user-event**：ユーザーから見える要素（役割やラベル）で操作するため、実装の詳細に依存しないテストにできる。
- **MSW**：fetch クライアントから TanStack Query まで本物のコードを動かせる。これにより、更新後にサイドバーとメインエリアの両方が最新になることを確認できる。
- テストの対象は、課題で明示された制約であるバリデーション（境界値の単体テスト）と、要件の中心である編集・追加・削除の流れ（結合テスト）を優先した。E2E は実装時間を考えて見送った。

## コンポーネント設計

### 選択中のコンテンツの状態を App で持つ

- 選択中のコンテンツ ID は、サイドバーとメインエリアの両方で使うため、共通の親である `App` で持ち、props で渡す。

### 責務の分割：API の型と入力のスキーマ

- API に送る値の型（`api/types.ts`）と、画面の入力ルール（`lib/contentSchema.ts` の Zod スキーマ）は、今は同じ項目（タイトル・本文）を持っているが、あえて別々に定義している。
- API の型は「バックエンドとの約束」、スキーマは「画面の入力欄とそのルール」であり、変わる理由が違う。
- コンポーネントが API の型に依存するのは、`handleSubmit` の中で `mutate` を呼ぶ箇所（API との境界）だけに限定している。

### 読み込み中・取得失敗の表示：Suspense + Error Boundary
- エラー処理やローディングはコンポーネントの中で分岐させない。
- **表示の責務に集中させたい**：境界として外側に宣言すると、コンポーネントは「データが取れている前提」で書ける。
- `useSuspenseQuery` の `data` は `undefined` を含まない型になるため、型の上でも分岐が不要になる。
